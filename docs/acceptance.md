# 実環境で確認する項目

自動検証で確認した範囲と、利用環境を用意して確認する範囲を区別します。

## リポジトリ内の検証

`uv run python -m unittest discover -v`で、ダウンロードの検証、プライベートリレーの指定、T3の宛先固定、通知の重複抑止、本文の明示的な受信確認を確認します。
`uv run waa smoke`で、実際の固定エンジンとリレーを起動し、合成セッションの送受信と両端の再起動後の復旧を確認します。
JSONの`ok`が偽ならコマンドも失敗します。
この検証は、モデルによる作業や人間が開いている会話の再開を実行しません。
Piがインストールされた環境では、別途隔離したPiプロセスとローカルの合成モデルを使い、実エンジンへの着信から返答までを確認します。
CIではPi 0.87.1をプロジェクト内だけに取得してこの確認を実行します。

## VPN上の2台通信

1. 承認された検証用の2台を同じTailscaleまたはNetBirdネットワークへ参加させます。
2. 有効なTLS証明書を使ったirohリレーを、VPNのIPで起動します。
3. 両端に同じ固定バージョンを取得し、チーム作成と招待による参加を実行します。
4. 通信先を観測し、Reasonやn0の探索とリレーを使わずに接続できることを確認します。
5. 直接接続するQUICの経路も確認し、必要な場合はVPNインターフェースへの制限を追加します。
6. 宛先の切断と再接続後に、元のIDのメッセージが重複せず届くことを確認します。

TLS、VPNの経路、端末のファイアウォールは、ループバックでの成功だけでは確認できません。

## 実エージェントの受信と再開

Pi 0.87.1は、[専用拡張](pi.md)と合成モデルで着信から返答までを確認します。
普段のモデルと既存拡張を併用した動作は、利用する環境で別途確認します。
Claude Code、Codex、Cursorも、利用するバージョンごとにネイティブな起動と受信フックを確認します。
起動時とフック実行時の両方で、同じ状態ディレクトリを使う必要があります。
作業中の受信と、待機中の会話の再開を別々に試します。
自分宛ての会話を選ぶこと、別プロジェクトの会話を公開しないことも確認します。

## T3の実環境

[T3の手順](t3.md)に従い、承認された資格情報と検証用スレッドを用意します。
待機中、処理中、通知結果が不明なままの再起動を試し、通知、本文の読取、明示的な受信確認を観測します。
別のスレッドが同じMCP設定を共有して受信箱を読めないことを確認するまでは、チームでの運用完了とは扱いません。

Grok Botのようなホスト型アシスタントは、非公開の接続先へ到達できる仕組みを別途必要とします。
公開ゲートウェイを用意する案は、VPN内だけで通信する要件と分けて判断します。
